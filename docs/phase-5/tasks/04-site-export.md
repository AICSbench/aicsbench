# Task 4: `aicsbench site export`

**Repository:** `aicsbench/aicsbench` (this one) · **Branch:**
`feat/phase5-site-export` · **Depends on:** tasks 1 and 2 (rebuild-mode
`validate_bundle`). The task 7 columns are optional in the export models;
if task 7 is not merged yet, the second of the two PRs adds them · **Commit scope:** `site`, `cli`

## Why

The website lives in `aicsbench/web` (decision D9) but must show exactly
the numbers the CLI computes. So every number, grouping and page path is
computed here, by the same `comparison.compare_trials`, and written as a
versioned export. The web repository only renders it.

## Command

```
aicsbench [--tasks-dir DIR] site export --data DIR --out DIR --base-url URL
```

- `--data`: a checkout of `aicsbench/data` (reads `submissions/` and
  `verified-runs.txt`).
- `--out`: output folder, emptied first.
- `--base-url`: absolute URL the site is served from, stored in
  `export.json` for canonical links and the sitemap.
- Task names and descriptions come from the normal task catalog (global
  `--tasks-dir`). A task in the data but not in the catalog is listed by ID
  only.

## Changes

1. `src/aicsbench/site/` (no new dependency; no HTML is produced in
   this repository):
   - `load.py`: read every bundle under `submissions/` and validate it in
     rebuild mode (`check_catalog=False`, see
     [schemas.md](../schemas.md#validation-rules)). Skip any bundle that
     still fails, with a warning. Attach `verified`, `logs_available`,
     `submitted_at` and `submitter`.
   - `slugs.py`: the slug rule in
     [schemas.md](../schemas.md#site-layout), with the collision check.
   - `pages.py`: build every page in the layout table as the `pages.json`
     structure in [schemas.md](../schemas.md#pagesjson).
     - Leaderboard rows come from `comparison.compare_trials`.
     - Sections are split by the dimensions each comparison must hold
       fixed. A comparison only ever groups trials with one
       `comparability_key`.
     - A task with several keys (for example two task versions) gets one
       section per key, newest task version first.
     - Within one key, trials are also split by `acceptance_suite_sha256`,
       so runs scored by different acceptance tests are never ranked
       together. The section heading names the suite hash's first 8
       characters when a task version has more than one.
     - Verified and community runs go in separate sections.
   - `comparison.compare_matrix(trials, rows, tasks, filters)` (in
     `src/aicsbench/comparison.py`, beside `compare_trials`): one column
     per `(task, task_version)`, and each column is exactly
     `compare_trials(by=rows)` on that task's trials with the same filters,
     including its refusals. A column that is refused carries the refusal
     message instead of cells. Rows are the union of the columns' groups.
     The overall columns follow task 5 item 6. `aicsbench compare` gets
     `--tasks t1,t2,...` (alias `--matrix`), which prints this table; with
     one task it behaves as today.
   - The `/leaderboard/` page: `compare_matrix` with rows `harness_model`,
     every task at its newest version, verified runs only, one section per
     stack.
   - `models.py`: pydantic models (`extra="forbid"`) for `export.json`, a
     trial row, `meta.json` and `pages.json`. The export is written through
     them, and `schema/*.schema.json` is generated from them.
   - `export.py`: write the export layout in
     [schemas.md](../schemas.md#site-export), including
     `export_schema: 1`, the data repository commit (`git rev-parse HEAD` in
     `--data`, but only when `git -C <data> rev-parse --show-toplevel`
     resolves to `--data` itself; a folder inside some other repository, or
     no repository, gives `null`), and copies of each
     accepted bundle's `submission.json` and `manifest.json` under
     `runs/<run_id>/`.
2. `tests/fixtures/site-export/`: a committed export produced from the
   fixture data folder below, regenerated by a documented command
   (`python -m tests.regen_site_export`). `aicsbench/web` copies this fixture
   for its own tests, so changing it is part of the contract.
3. Docs: `docs/phase-5/site-export.md` explains the command, the export
   schema version rule and how the web repository consumes it.

## Acceptance criteria

- [ ] Exporting a fixture data folder (two bundles: one verified, one
      community; two harnesses; two stacks) lists every page kind in the
      layout table, and the test checks a few known values in `pages.json`
      (a pass rate, a harness name, a run ID).
- [ ] Every leaderboard section's `rows` equal `compare_trials` on the same
      trials (the test compares both).
- [ ] `compare_matrix` over two tasks equals `compare_trials` per column,
      a row missing from one task is listed after the complete rows with
      its overall marked incomplete, and a refused column shows the
      refusal and is left out of the overall.
- [ ] An invalid bundle in the data folder is skipped with a warning, and
      the export still succeeds.
- [ ] Two models whose base slugs collide (`Foo/Bar`, `Foo-Bar`) get
      distinct page paths, and adding the second does not change the first's
      path. `Foo/Bar` and the literal value `foo-bar-c84b3c5b` (its suffixed
      slug) also get distinct paths. Two values whose suffixed slugs collide
      (`ABcdEfgHijkLMNopqrs` and `ABCDeFghijkLMnOPQrs`, both
      `abcdefghijklmnopqrs-577c43dd`) make the export fail with an error
      naming both, and write nothing.
- [ ] A bundle for a task version the catalog no longer ships still appears,
      under its own version.
- [ ] Unavailable means are `null` in `rows`, never `0`.
- [ ] Two bundles of one task version with different suite hashes land in
      different sections.
- [ ] `--data` pointing at a plain folder inside this repository records
      `data_commit: null`.
- [ ] Submitted strings (`submitter`, `notes`, model, harness) are copied
      unchanged (no HTML escaping here). The fixture includes
      `<script>alert(1)</script>` in `submitter.name` and `notes`, so the
      web repository can test its escaping.
- [ ] The fixture export validates against its own `schema/*.schema.json`
      (the test uses the `jsonschema` package as a test-only dependency).
- [ ] The core install gets no new dependency.
